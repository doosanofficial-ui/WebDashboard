# Preserve recent owned Simulator boot events

The first 24c9886 CI Korean maximum-text group failed before app build/install/UI: bootstatus reached its unchanged 180-second limit with 0 bytes of output. The UUID event stream stopped at its 2 MiB input cap, leaving the last 143.412 seconds before the first failure unobserved. Native-path sampling happened after the first failure, and the diagnostic worker produced no entry receipt. The root cause remains unknown. Re-running an unchanged CI or increasing timeouts would not resolve this missing evidence.

The collector now retains a fixed prefix and a bounded recent tail through its existing 240-second read window. At the default 2 MiB payload limit it keeps a 1 MiB prefix in `simulator-boot-stream.ndjson`, then up to 512 KiB of subsequent complete events in `simulator-boot-stream-tail.ndjson`. It reserves another 512 KiB for atomic tail staging; head + old tail + temporary tail therefore stays within 2 MiB of file payload. Filesystem allocation blocks/metadata and process RSS are separate from this payload bound. Head and tail do not overlap and preserve receive order. Foreign UUIDs, invalid JSON, nonstring messages and oversized lines remain excluded. Each read is at most 64 KiB, and an unfinished line stays bounded at 64 KiB after each batch. A complete valid record too large for the tail budget is skipped and counted, rather than split into a false event.

Only a changed tail is checkpointed, at most once per second during the read loop, including quiet stdout. The final optional publication follows pipe closure and owned process-group cleanup. Tail records are written sequentially to a unique exclusive temporary file and atomically replace the prior completed tail; no payload join copy is created. Disk I/O does not hold the state lock. A failed replacement preserves the prior tail and its last successful saved statistics; there is no repeated write retry. An unfinished writer keeps workerStopped/collectorCleaned false. Atomic replacement protects completed snapshots but does not promise durability after power loss.

Receipt schemaVersion 2 explicitly removes the lifetime input-byte cap: inputBytes counts actual bytes drained during the existing read window. savedBytes/events still describe the legacy prefix file. Tail buffered statistics are separate from tailSavedBytes/tailSavedEvents and the monotonic receive interval of the last successful publication. Errors and tailPublishFailed label unavailable or stale evidence. Collector cleanup success does not establish service health, all-event coverage or a boot fix.

Continuing to drain may use more CPU/I/O than stopping after 2 MiB; memory/file retention alone does not cap parser work. At the default tail size, periodic full snapshots can write roughly 120 MiB over 240 seconds, plus initial/final writes. Changed-only checkpoints and sequential writes bound avoidable work. The 240-second value bounds new reads, not a synchronous disk operation that is already blocked or subsequent process cleanup waits. Existing boot 60/bootstatus 180, diagnosis 20/probe 3, app build 600/UI 1200, original exceptions, selectors and owned cleanup are unchanged. The Telemetry app and existing user/vehicle data are untouched.

Seven added regressions cover a marker after the former input cap, foreign/invalid/oversized traffic before a late owned event, previous snapshot retention and actual staging payload on replacement failure, a valid record exceeding the tail budget, a blocked writer's independent incomplete snapshot, a quiet stream checkpoint before stop/EOF, and no new read after a blocked publication returns beyond stop/deadline. The late-marker/filter/replace quiet-stream and read-return boundary cases were observed RED on their previous implementations before GREEN. Existing real owned-child TERM-output and original boot-exception regressions remain applicable. All fixture signals target newly created test-owned process groups.

Source base and failure evidence: 24c98869c191d9ac5dfa7247ced6e46331516823, Native Reliability run 37834149921/attempt 1. The actual unique 31 UI gate failed; planned SE reexecution passed 2/2. This change improves future observation, and does not claim that the original KO/SE, Route container, Replay background waiter or Layout launch/deadline failures are fixed.

Validation on the candidate: all 169 script regressions passed in 12.546 seconds; platform documentation parity and scoped diff checks passed. Independent read-only review found no remaining Critical/Important issue. A new synthetic owned producer emitted 16,783,838 bytes: the 24c9886 collector stopped at 2,097,152 input bytes and lost the final marker; the candidate retained the marker in a 491,791-byte tail with a 1,016,170-byte prefix. Both owned process groups were cleaned. This single local burst used 0.036 collector CPU seconds and 0.070 wall seconds on the candidate, versus 0.008/0.036 on the earlier capped collector; these measurements do not establish remote host overhead or Simulator health.
